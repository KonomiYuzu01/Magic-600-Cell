## 2. Actual problem and reproduction

- At `97815b1`, `check_run.py` accepts `runner-run/3` (`FORMATS`, :57) and hands every v3 row with
  `phase == 'lattice'` to `check_lattice.replay_lattice_step` (:1186-1195). The stub (`check_lattice.py:65-87`) reads
  the whole word into a Python list (`read_ia16`, :48-62), plays every letter through `State.apply` (:77-86) and
  appends `unchecked_contract` to its result (:87). It does not recompute `labels_identity`, and it does not compare
  the tree's `inverse_of` and `same_as` ranges, which `check_run.py` leaves to `check_lattice.py` for lattice rows
  (`check_tree` docstring, :466-469; the comparison is skipped when the word is not held, :552). So a v3 record with
  a played lattice fails as `unchecked_contract`, or passes only with `--allow-unchecked-contracts` (`step_row` and
  `merge`, :1033-1046), as I0's own test asserts (`test_check_run.py:1655-1661`).
- Records of format 1 and 2, and v3 records labelled `lattice_composition`, still check the lattice phase by running
  `verify_late.py` (`lattice_check`, `check_run.py:888-1017`, called at :1307-1311; such a v3 record gets no end
  digest, :1315-1316). That verifier "checks the lattice word by composing permutations, not by playing it" (stage 13
  `README.md:564-565`; stage 12 `PROOFS-B.md`, R22D-57).
- The stub's loop is too slow for lattice words. It plays every letter through `State.apply`, as the checker's main
  loop does (`check_run.py:1207-1216`). On a lattice configuration that takes about 15 ms per retained letter
  (integrator measurement, 20 October 2026: 50 letters in 0.73 s), so the 8,701,310 retained twists of the D0

  162,994,641 twists (decision page :93-94). The plan's estimate for the D0 check with a fast model is about
  7 minutes. Its `read_ia16` also builds one Python list per letter, which does not fit memory for such words.
- Reproduction: read `check_run.py:1186-1195`, :465-557 and the stub `check_lattice.py` at `97815b1`, and
  `test_check_run.py:1655-1689`. No command is needed.

### 4.2 The rows and files P5 reads (plan section 1; at `97815b1` the runner's `played_lattice` writes them)

- Row keys (plan section 1, "Every step"): `index, phase, subphase, rule, word, letters, encoding, word_sha256, tree,
  contract, gate, standing, before{digest, off, heights}, after{…}, seconds, attempts`, plus the step's own fields.
  The runner writes a lattice row in `played_lattice` (`runner.py:1357-1361`): these core keys with `attempts: []`,
  then the fields of P3's `LatticeStep` (`runner_api.py:61-79`). Only the last lattice row also has `table`, the end
  table (`runner.py:1363-1365`). `ROW_KEYS` (:66-67) and `FORBIDDEN_KEYS` keep a step's fields off the core keys
  (:1334).
- A lattice row: `phase: 'lattice'`, `subphase: null`, `rule` `lattice/orbit-<o>` or `lattice/correction-<k>-<macro>`,
  `contract: 'lattice_literal'`, `gate: 'player'`, `standing: 'rule'`, `encoding: 'ia16'`,
  `word: 'words/NNNNN.ia16.gz'`, `tree: {file: 'step-trees/NNNNN.json.gz', sha256, size}`, and `before` and `after`
  each `{digest, off: 0, heights: {}}`. A lattice configuration has no off piece, so its height histogram is empty
  (`lattice_snapshot`, `runner.py:205-209`; `Mechanics.heights`, :240-249). The last lattice row carries
  `labels_identity` (plan section 1, "Lattice"); the runner refuses a played phase whose last step does not claim
  `true` (:1343-1344). The other fields (P3's `orbit`, `factor_first`, `correction`, `macro`, `times`, …) are not
  P5's; ignore unknown keys.
- What the runner checks before it records a played phase (`runner.py:1325-1349`; I0-02): each step's contract, gate,
  standing and encoding; that the first `before` is the runner's own snapshot, each later `before` the previous
  `after`, and each `after` a lattice snapshot; the word file against `word_sha256` and `letters`; the tree against
  its sha256 and size; the last step's `labels_identity`; and that the end table loads to the last `after`. It never
  replays a lattice word. None of this is evidence for the checker: P5 checks the files again on its own.
- `ia16` words (plan section 1): "gzip with mtime 0 of little-endian uint16 codes `60·grip + item`, all below 36,000;
  `word_sha256` is taken over the uncompressed bytes". The producer is `runner_api.Ia16Writer`
  (`runner_api.py:234-265`): it writes into `gzip.GzipFile(filename='', mode='wb', fileobj=..., mtime=0)` (:241);
  `write_codes` rejects a code of 36,000 or more (:247-248), byte-swaps on a big-endian host (:249-250) and updates
  the sha256 with the same bytes (:252-253); `close` returns `{'sha256', 'letters'}` (:259-265).
  `ia16_code(grip, item)` is `60 * grip + item` (:228-231). The runner's reader `ia16_digest(path)` (:268-290)
  recomputes those two values from a file in 1 MiB chunks and raises `ValueError` for a bad header, an odd byte count
  or a code of 36,000 or more (the runner calls it at `runner.py:1337-1338`). Both are runner code: test oracles
  only, never imported by `check_lattice.py`. A `json` word's `word_sha256` is something else, the sha256 of
  `json.dumps(word)` (`runner.py:100-101`); P5 does not read `json` words.
- Step trees (plan section 1): a part is `{name, letters, parts: [...]}` or `{name, letters, span: [from, to]}` (end
  excluded). A part may carry `inverse_of: [i, j, …]` or instead `same_as: [i, j, …]`, "the index path from the root
  to an earlier part (earlier in depth-first order, so its span ends at or before this part's start) with the same
  number of letters". `inverse_of`: "Its letters are that part's letters, inverted and in reverse order" (examples:
  V⁻¹ of a closure, which names V; the trailing u^(us) factor of a `conj` node, which names the leading u^(−us)
  factor, R3-02). `same_as`: the letters equal that part's letters, and the two parts have the same name. "A reference
  to a later part fails as `tree_malformed`." The checker checks that "every `inverse_of` range equals the inverse of
  the range it names, letter by letter, through the menu's inverse table" and that "every `same_as` range equals the
  range it names, letter by letter, and the two parts have the same name".
- Index paths and order: the root has the path `()`, and child `i` of a part with path `p` has `p + (i,)`. Parts are
  visited depth-first in pre-order, the root at depth 1 (`runner_api.walk`, :165-172). A reference is valid when the
  named part was visited earlier, ends at or before the referring part's first letter, has the same letters and, for
  `same_as`, the same name: the runner's self-check `runner_api.check_tree` (:179-207, references :197-203) and
  `check_run.check_tree` (:537-551) apply exactly this rule, so a reference to a later part, or to a non-empty
  ancestor, is rejected by both. P5 applies the same rule.
- The tree file is gzip (mtime 0) of `json.dumps(root, separators=(',', ':'), allow_nan=False) + '\n'`, its sha256
  over the uncompressed bytes; `runner_api.write_tree(path, root, letters)` runs `check_tree` first and returns
  `{'sha256', 'size'}` (:210-214), and `runner_api.read_tree(path)` returns the root and that sha256 (:217-223; a test
  oracle only). P5 reads the file itself (section 4.1, interface gap).
- The lattice trees P3 writes (plan section 3, P3 "Step trees"; stage 13 `README.md:680-688`): an orbit step's root is
  the orbit, then its factors, then the `conj` and `prod` nodes, then the `word` and `path` leaves as spans. A `conj`
  node expands to u^(−us)·x^(sign)·u^(us), and its trailing u^(us) part carries `inverse_of` the leading part. A node
  whose subtree would take the tree over 10⁶ parts is one span. A correction step's tree is the macro, named; a
  repeated part carries `same_as`. Trees have at most about 10⁶ parts and depth at most 64
  (`runner_api.TREE_MAX_DEPTH`, :29; `check_run.TREE_MAX_DEPTH`, :79).

### 4.4 The fast model and the dispatcher (plan P5; decided here where marked)

- The model holds `labels` (an integer array of NS entries: the home slot of the sticker in each slot) and
  `place_pose` (an integer array of NP entries: the K+ index held at each place).
- From a `State` on the lattice: the labels from `lattice_stickers()` (with `frame_agrees` everywhere), and, with
  `k = state._kpose()[state.pose_id]`, `place_pose[piece_of[orbit_of, compose_vec(k, transport)]] = k`, which must be
  a bijection onto all places.
- A retained letter (c, i) with K+ element g = `index_of_matrix(element(menu, c, i))`: play `a4_word(c, g)`. For each
  signed id m, with j = |m| − 1: the slot move `(src, dst)` of generator j, swapped when m < 0, gives
  `labels[dst] = labels[src]` (NumPy evaluates the right side first); the place move `(move_src[j], move_dst[j])`,
  swapped when m < 0, with r = `gen_idx[j]`, or `inv[gen_idx[j]]` when m < 0, gives
  `place_pose[pd] = compose(r, place_pose[ps])`. Precomposing a letter into one gather, or tabulating r∘k for all k,
  is allowed when the result is identical. The words at grip 5 (integrator measurement; re-checked at `97815b1`):
  item 0 → [], 1 → [11] (H_5), 2 → [12] (T_5), 5 → [−12]; items 3, 4, 8 and 9 → two ids; items 6, 7, 10 and 11 →
  three ids. An orbit step's word written by P3 has one generator or its inverse per letter (for example items 1, 2 and 5
  at grip 5); a correction step's word holds the library macro's own letters (section 4.6).
- Back to a `State`: for every slot s, the home piece `slot_piece[labels[s]]` gets the pose `place_pose[slot_piece[s]]`
  (all slots of one piece must agree). Build `State(ctx, menu=menu)` with those K+ poses (`_intern_k`, `_compact`),
  then require that its `lattice_stickers()` labels equal the model's labels and that `frame_agrees` holds; otherwise
  the failure is `model_labels`.
- Dispatcher (plan: "used only while the state is on the lattice and the letter is a retained item at its grip; any
  other letter goes through `State.apply` with the admissible and certain checks"):
  - a retained letter while the configuration is on the lattice goes to the model, built lazily from the `State`
    when it is first needed;
  - any other letter: if the model is active, write it back into the `State` first; then `State.apply` with the checks
    of section 4.3. A retained letter off the lattice also goes through `State.apply`; w9's fifth letter (section 4.6)
    is one;
  - after a `State.apply` letter, return to the model only at a retained letter where `state.is_lattice()` holds. A
    switch costs one conversion (`lattice_stickers()` takes about 0.1 s, integrator measurement). Staying on
    `State.apply` for the rest of a short correction step is allowed (decided here). An orbit step of retained letters
    on the lattice must run entirely on the model; test D checks this through `stats`.
- Guard (decided here; the plan's acceptance lists "a non-retained letter on the fast path" as a failure):
  `LatticeModel.play(code)` checks the code against the model's own table of retained items, built from the menu when
  the model is made, and raises `FastPathError` for any other code, changing nothing. The dispatcher decides through a
  separate module-level predicate, `fast_letter(code, on_lattice)`, which a test can patch. A non-retained letter that
  reaches the model is never applied, and the replay reports `fast_path`.
- `LatticeModel.from_state(state, menu)` refuses a `State` that is off the lattice. `LatticeModel.to_state()` returns
  the rebuilt exact `State`. `labels` is readable. Other names are yours.
- Load the model data (`primitives()`, the move arrays) on first use, not at import: `check_run.py` imports
  `check_lattice` for every record (:46).
- Exact data only: integer arrays and exact K+ indices; no float decision.

### 4.5 Entry points and failure names (decided here unless section 4.1 fixes them)

`read_ia16(path, sha256=None)`: the stub's contract (section 4.1).

The streaming reader (names yours; this packet calls them `ia16_info` and `Ia16Error`):
- streams the gzip file in chunks of at most `CHUNK_BYTES` uncompressed bytes, a module-level constant that every
  reader looks up when it is called, so that test B can lower it (memory independent of the word's length; a chunk
  may end in the middle of a code, which carries to the next chunk), requires the stub's header (magic
  bytes and mtime 0, stub :51-52), an even number of bytes and every code below 36,000, takes the sha256 of the
  uncompressed bytes, and decodes little-endian (`'<u2'`);
- returns `{'letters', 'sha256'}`; a chunk iterator over `uint16` arrays serves the replay;
- raises `Ia16Error('word_file')` (a `ValueError` that carries the failure `name`) for a missing or unreadable file, a
  file that is not gzip, a header whose mtime is not 0, a truncated or corrupt stream, or an odd byte count, and
  `Ia16Error('word_literal')` for a code of 36,000 or more (`word_literal` is `check_run.py`'s name for an invalid
  letter, :248-250). No path or exception text reaches the caller.

`ia16_ranges(path, ranges)`:
- `ranges` is a list of `(start, end)` with 0 ≤ start ≤ end, in any order, possibly overlapping. One pass over the
  file (the plan's "second pass") returns the codes of each range as a `uint16` array, in the order given. A range
  past the end of the file raises `Ia16Error('word_file')`.

`replay_lattice_step(state, row, path, menu, *, stats=None)`:
1. Row fields P5 needs before reading: `encoding == 'ia16'` (`encoding`), `letters` an integer of at least 0
   (`letters`) and `word_sha256` 64 lowercase hexadecimal digits (`word_sha256`). Any of these stops the call before
   play. The other labels belong to `check_run.py` (section 4.1).
2. Verify the word before any play: `ia16_info(path)`; its letter count equals `row['letters']` (`letters`) and its
   sha256 equals `row['word_sha256']` (`word_sha256`). After any of these, or an `Ia16Error` (its name), return
   without the tree check and without playing, as `check_run.py:1101-1112` keeps invalid literal data from the
   simulator.
3. Tree ranges: locate and read the tree (section 4.1, interface gap) and run `check_tree_ranges`. Its failures are
   recorded; they do not stop the replay (decided here: the word itself is verified, and the tree only presents it).
4. Replay in a second pass, chunk by chunk, through the dispatcher of section 4.4. A `State.apply` letter that is not
   applied or is uncertain, or a simulator exception, gives `admissible` and stops; a model refusal gives `fast_path`
   and stops.
5. Step end, when the replay finished: the exact `State`, rebuilt from the model with the label cross-check
   (`model_labels`), or the one played. `row['after']['off']` must be 0 and equal the state's off count, and
   `row['after']['digest']` must equal the state's digest (`after_off`, `after_digest`, the names of
   `Snapshot.check`). `labels_identity` is whether the end is on the lattice, its `frame_agrees` holds everywhere and
   its labels equal `arange(NS)` (the runner side's labels also require frame agreement, `literal_lattice.py:215-221`).
   A step end on the lattice where `frame_agrees` fails anywhere gives `model_labels`, whether it was reached on the
   model or through `State.apply` (decided here; an edge case: frames agree at T and at the twelve invisible-rotation
   candidates tried in a re-check at `97815b1`). When the row has `labels_identity`, it must be a bool equal to that
   value (`labels_identity`); off the lattice the value is false.
6. On return, the `state` object holds the end configuration: after success, the end of the step; after a stop in
   step 4 or 5, the last exact configuration reached; after a stop in steps 1 or 2, the configuration it came with.
   Write a rebuilt `State` into it in place (`pose_id`, `_poses`, `_lookup`; `journal = []`; `_anchor_cache = {}`), as
   `load_table` does (`check_run.py:176-180`), so that `Snapshot(st)` (:186-194, :1233) sees it.
7. Return the failure names in the order found, without duplicates, and `[]` when the step passes. An unexpected
   exception is caught and reported as `lattice_step`, the name `check_run.py` gives a crashed call (:1192-1193),
   never as a pass and without its text.
8. When a dict is given as `stats`, fill in `letters`, `fast` (letters played on the model), `simulated` (letters
   played through `State.apply`), `switches`, `labels_identity` (a bool, or `None` when the end was not reached),
   `digest` (the end digest, or `None`) and `seconds`.

`check_tree_ranges(path, root, menu)` (P5's own helper; `check_run.py` does not call it):
- Walk the tree iteratively (up to about 10⁶ parts; no recursion that a deep tree could exhaust) and compute each
  part's range [lo, hi) from its spans. Report `tree_malformed` for anything the range check cannot rely on: a part
  without a non-empty string name; both or neither of `span` and `parts`; empty `parts`; spans that are not contiguous
  from 0; a `letters` value that does not match its span or the sum of its parts; depth over 64; or root letters other
  than the word's letter count. `check_run.check_tree` has already rejected all of these before a replay
  (section 4.1), some of them under the names `tree_length` and `tree_expansion` (:515-534); the walk repeats them
  only so that a direct call never compares unchecked ranges.
- For each part with `inverse_of` or `same_as` (both on one part: `tree_malformed`): the named part must exist, come
  earlier in pre-order, end at or before this part's start (`named.hi <= part.lo`) and have the same letters; for
  `same_as` it must also have the same name. Otherwise `tree_malformed`; this covers a reference to a later part
  (R3-02). It is the rule of `check_run.py:537-551`.
- Read every referenced range with `ia16_ranges` in one pass and compare letter by letter. `inverse_of` requires
  `part[t] == inverse(named[len − 1 − t])` for every t, with `inverse(code) = 60 * (code // 60) + inv_item[code % 60]`
  and `inv_item` the menu's inverse table, built as `inverse_items` builds it (`check_run.py:388-391`). `same_as`
  requires equal codes. A difference gives `tree_expansion`, the name `check_run.py` gives the same difference on a
  word it holds (:552-557).
- A reading error gives its `Ia16Error` name. Return the failure names, `[]` when every range holds.
- Scope (decided here): plan section 2 names only `inverse_of` for P5, because `same_as` came later as an integrator
  amendment (plan section 1); section 1 requires the checker to check both, `check_run.py` compares neither on a
  lattice word, and the stage 13 README says P5 checks a lattice step's ranges (`README.md:510-511`). So P5 checks
  both on `ia16` lattice words.
- Memory: at most about 2 bytes per letter of the word plus the tree. Decoding the referenced ranges, or the whole
  word, into `uint16` is fine.
