# Level 2: framework facts checked at the pinned versions

`HARNESS.md` line 3 lists framework facts as assumed until the integrator checks them. Claude checked these on 2026-10-04 against the sources at tag `4.7.2-stable` (github.com/godotengine/godot) and tag `v6.10.3` (github.com/qt/qtbase and github.com/qt/qtdeclarative). Paths are relative to each repository. Source evidence only: each fact still needs the runtime check named with it.

## Godot 4.7.2

| # | Fact | Source | Consequence for L2-G | Runtime check |
|---|---|---|---|---|
| G1 | `WINDOW_MODE_FULLSCREEN` is the multi-window mode: the window is moved to the screen rectangle plus a 2-pixel overhang (`_get_screen_expand_offset`), and a window region clips the extra pixels. `WINDOW_MODE_EXCLUSIVE_FULLSCREEN` uses the exact screen rectangle. Both use `WS_POPUP` without a frame. | `platform/windows/display_server_windows.cpp` 220-243, 2215, 2582, 2794-2798, 2815-2826 | Use `ExclusiveFullscreen`; the backbuffer then equals the monitor's native size. | size checks of sections 4 and 7; the gate's `display == backbuffer` |

| G3 | `RenderingDevice.ScreenGetWidth/ScreenGetHeight(window)` are `_THREAD_SAFE_METHOD_` (callable from any thread). They return the window surface's size, which the display server sets on resize; the swap chain follows at the next frame. | `servers/rendering/rendering_device.cpp` 5427-5441 | Read the size once it has been stable for some frames, then create the ring (section 4). | `native.target` against the window and backbuffer sizes |
| G4 | `OS.GetCmdlineArgs()` returns only the arguments the engine did not consume. `--path`, `--rendering-driver`, `--disable-vsync`, `--log-file`, `--gpu-index`, `--gpu-validation` and the other engine options are consumed and left out; arguments after `--` go to `OS.GetCmdlineUserArgs()`. | `main/main.cpp` 1090-1093, 1331, 1349-1361, 1517, 1768, 1973, 2069-2073, 2250 | **Contradicts `HARNESS.md` section 6** as first written: `GetCmdlineArgs()` cannot supply the engine arguments. | G6 | The D3D12 context enumerates adapters in high-performance order (`IDXGIFactory6::EnumAdapterByGpuPreference(DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE)`). The device is `--gpu-index` if given; otherwise the first adapter with the highest type score, where discrete beats integrated unless the Windows per-app GPU preference for the executable asks for power saving. | `drivers/d3d12/rendering_context_driver_d3d12.cpp` 180-189, 355-372; `servers/rendering/rendering_device.cpp` 102-118, 8336-8361; `platform/windows/os_windows.cpp` 845 | No setting needed: the RTX 4070 comes first in that order. | G7 | `..._console.exe` starts the executable without `_console` as a suspended child process in a kill-on-close job object, waits for the job, and returns the child's exit code. | `platform/windows/console_wrapper_windows.cpp` 77, 128, 150-179 | The presenting process is the child. | G8 | `user://` resolves under `%APPDATA%` (`get_data_path`), the cache under `%LOCALAPPDATA%`, and `application/config/use_custom_user_dir` only changes the folder name under `%APPDATA%`. | G9 | The project assembly is loaded from memory. `PluginLoadContext.Load` runs for every assembly the context resolves itself (one not shared with the engine). It keeps the resolved path in the public `AssemblyLoadedPath`, replacing any earlier one, and calls `LoadFromStream`, so `Assembly.Location` is empty for the project's types. | `modules/mono/glue/GodotSharp/GodotPlugins/PluginLoadContext.cs` 15, 27-28, 53-69; `Main.cs` 139-151 | `godot:assembly` comes from the load context's `AssemblyLoadedPath`, after a check that the file's full assembly name is the running assembly's. | G10 | On Windows the process is system DPI aware, not per-monitor aware. With `display/window/dpi/allow_hidpi` at its default (true), `DisplayServerWindows` calls `SetProcessDpiAwareness(PROCESS_SYSTEM_DPI_AWARE)`, and the executable's embedded manifest declares no DPI awareness. | `platform/windows/display_server_windows.cpp` 7927-7929; `main/main.cpp` 2759; the manifest in `Godot_v4.7.2-stable_mono_win64.exe` | The Godot app accepts system awareness as well as per-monitor version 2. Its client rectangle and swap chain are then scaled, while `EnumDisplaySettingsW` reports physical pixels in every DPI context (Microsoft's `EnumDisplaySettingsW` documentation), so the window never settles. With the assembly-path fix, the first validation run (4 October) exited 1 with reason `dpi-awareness`. | every run records the awareness; the five sizes must be equal |

## Qt 6.10.3

| # | Fact | Source | Consequence for L2-Q | Runtime check |
|---|---|---|---|---|
| Q1 | `showFullScreen()` gives the window `WS_CLIPCHILDREN \| WS_CLIPSIBLINGS \| WS_POPUP` (plus `WS_SYSMENU` and `WS_VISIBLE` when they applied) and the monitor rectangle. `WS_BORDER` is added only with the opt-in has-border-in-full-screen flag, which is off by default. | `qtbase/src/plugins/platforms/windows/qwindowswindow.cpp` 1587-1588, 1634, 2759-2790 | `showFullScreen()` is enough; do not set the border flag. | size checks; `display == backbuffer` |
| Q2 | `Qt::WindowStaysOnTopHint` makes Qt call `SetWindowPos(HWND_TOPMOST)`. | same file, 1004-1005 | Set the flag before showing the window. | `samples_covered` and foreground samples |
| Q3 | With swap interval 0 in the window's requested format (or `QSG_NO_VSYNC`), the threaded render loop asks for `QRhiSwapChain::NoVSync`. The D3D12 swap chain then uses interval 0, adds `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` when tearing is supported, presents with `DXGI_PRESENT_ALLOW_TEARING`, and skips the frame-latency waitable object. | `qtdeclarative/src/quick/scenegraph/qsgthreadedrenderloop.cpp` 940-945; `qtbase/src/gui/rhi/qrhid3d12.cpp` 1835-1845, 6847-6857 | Set `QSurfaceFormat::setSwapInterval(0)` before the window is created. | PresentMon `SyncInterval` 0 and `AllowsTearing` |
| Q4 | `QQuickWindow::swapChain()` (since 6.6) returns the window's swap chain under the basic and threaded loops. `QRhiSwapChain::currentPixelSize()` is the size of the last successful build, and the documentation recommends reading it on the rendering thread. | `qtdeclarative/src/quick/items/qquickwindow.cpp` 4133-4147; `qtbase/src/gui/rhi/qrhi.cpp` 7658-7680 | Read the backbuffer size on the render thread. | size checks |
| Q5 | When Qt creates its own D3D12 device, the adapter is `QT_D3D_ADAPTER_INDEX` if set; otherwise the LUID given by `QQuickGraphicsDevice::fromAdapter` (or `fromRhiAdapter`); otherwise the first `EnumAdapters1` adapter. `fromAdapter` only passes the LUID, so Qt still creates and owns the device (route `qt`). | `qtbase/src/gui/rhi/qrhid3d12.cpp` 156-177, 257-310; `qtdeclarative/src/quick/scenegraph/qsgrhisupport.cpp` 1249-1257 | Without a setting, Qt takes DXGI's first adapter, which was the RTX 4070 in level 1 on the owner's machine (its README). A robust choice is `fromAdapter` with the LUID of `EnumAdapterByGpuPreference(HIGH_PERFORMANCE)` index 0. | `environment.adapter`; the finalizer's `adapter` refusal |
| Q6 | `QRhi::driverInfo().deviceName` is the adapter's `DXGI_ADAPTER_DESC1::Description` in UTF-8. | `qtbase/src/gui/rhi/qrhid3dhelpers.cpp` 81-89; `qrhid3d12.cpp` 304 | Matches the names S-B and the DLL report. | `adapter` and `presenting_adapter` |
| Q7 | `QQuickGraphicsConfiguration::setDebugLayer(true)` (default false; `QSG_RHI_DEBUG_LAYER=1` sets it too) makes the D3D12 backend call `ID3D12Debug1::EnableDebugLayer` before it creates its device. | `qtdeclarative/src/quick/items/qquickgraphicsconfiguration.cpp` 510-528, 829-831; `qsgrhisupport.cpp` 1124, 1245; `qrhid3d12.cpp` 243-250 | Validation runs set it; other runs leave it off. | `debug.debug_layer` from `sa2_device_info` (`validation` and `debug-switch` refusals) |
| Q8 | The D3D12 swap chain's size is the window's logical size times its device pixel ratio, rounded (`QD3D12SwapChain::surfacePixelSize`). At a pass-through factor of 1.5 (the owner's 150 %), a 2560 x 1600 monitor gives a 1707 x 1067 logical window and a 2561 x 1601 backbuffer. `QT_ENABLE_HIGHDPI_SCALING=0` turns off platform DPI scaling, so the ratio is 1. `QGuiApplication::setHighDpiScaleFactorRoundingPolicy(Floor)` would also give 1 at 150 %, but `QT_SCALE_FACTOR_ROUNDING_POLICY` overrides it. | `qtbase/src/gui/rhi/qrhid3d12.cpp` 6699-6703; `qtbase/src/gui/kernel/qhighdpiscaling.cpp` 322-345, 398, 423, 438-446, 468; `qguiapplication.cpp` 4037-4042 | `launch.json` sets `QT_ENABLE_HIGHDPI_SCALING=0` (level 1's value), and `configuration` records it. | size checks; a launch without it fails at the first frame (`fullscreen-size`) |
| Q9 | A failed `endFrame` returns `FrameOpError` when the command list does not close, when there is no swap chain, or when `Present` fails other than by device loss. The D3D12 backend logs its own warning and returns before the completion signal and the frame-slot advance. Both render loops then log `Failed to end frame` and still emit `afterFrameEnd`. Only `FrameOpDeviceLost` goes to device-loss handling. The warning is a plain `qWarning` in the default category. Qt drops it before any message handler when logging rules (`QT_LOGGING_CONF`, `QT_LOGGING_RULES`, `qtlogging.ini` files or `setFilterRules`) disable that category's warnings. A category filter runs again after every rule update. | `qtbase/src/gui/rhi/qrhid3d12.cpp` 1824-1828, 1832, 1840-1852, 1859, 1872; `qtdeclarative/src/quick/scenegraph/qsgthreadedrenderloop.cpp` 788-799, 815-818; `qsgrenderloop.cpp` 709-722; `qtbase/src/corelib/global/qlogging.cpp` 2117-2121, 2374-2381; `qtbase/src/corelib/io/qloggingregistry.cpp` 335-383, 391-400, 452-476 | `afterFrameEnd` alone does not prove a present. Before `QGuiApplication` starts, L2-Q installs two things. A category filter applies the previous filter, then keeps the default category's warnings on. A message handler chains to the previous one, which is Qt's default handler. After that warning, the app marks no frame shown and fails the run with reason `present` (exit 1). | No failed `Present` is possible without a fault inside Qt. `check_project.py` pins the filter, the handler and their order before `sa2_mark_shown`. An experiment compiled the watch code from `l2.cpp` against QtCore 6.10.3 and tested three setups: `default.warning=false` rules, `*.warning=false` rules and a `QT_LOGGING_CONF` file. The 092463b code missed the warning in all three; the current code saw it, and Qt's default handler still wrote it. |
| Q10 | The threaded render loop asks for each frame with `QWindow::requestUpdate()` (`update` and `maybeUpdate` reach it through `postUpdateRequest`). On Windows, `QWindowsWindow::requestUpdate` hands the request to the DXGI vblank service when the window has a DXGI output: a thread waits on `IDXGIOutput::WaitForVBlank` and then posts the update to the GUI thread. Update-driven frames are therefore paced at the display's refresh whatever the swap interval. `QT_D3D_NO_VBLANK_THREAD` set to a nonzero integer turns the service off. `requestUpdate` then uses `QPlatformWindow::requestUpdate`, a precise 5 ms timer (`QT_QPA_UPDATE_IDLE_TIME` replaces the 5 ms; above 60 Hz the default is divided by refresh/60). | `qtdeclarative/src/quick/scenegraph/qsgthreadedrenderloop.cpp` (`update`, `maybeUpdate`, `postUpdateRequest`); `qtbase/src/plugins/platforms/windows/qwindowswindow.cpp` (`QWindowsWindow::requestUpdate`); `qtbase/src/gui/rhi/qdxgivsyncservice.cpp` (constructor, vblank thread); `qtbase/src/gui/kernel/qplatformwindow.cpp` (`requestUpdate`) | The Qt app asks for the next frame from `frameSwapped`, so the vblank wait paces it. The owner's level 2 Qt runs of 4 October measured 60.00 fps with p99 about 17.4 ms in every scene, with `SyncInterval` 0 and tearing allowed: their frame rate shows this cap, not GPU headroom. An uncapped Qt measurement sets `QT_D3D_NO_VBLANK_THREAD=1` and `QT_QPA_UPDATE_IDLE_TIME=0`. Both are `QT_*` variables, so they enter `configuration` and give another build identity. | a short W3 run with both variables runs above 60 fps (PresentMon `msBetweenPresents`) |

## PresentMon 2.6.0

Checked by Claude on 2026-10-09 against tag `v2.6.0` (github.com/GameTechDev/PresentMon). Q10 was checked the same day against the Qt tags above.

| # | Fact | Source | Consequence for L2-F | Runtime check |
|---|---|---|---|---|
| P1 | PresentMon sets a present's `AllowsTearing` (`SupportsTearing`) only in the kernel handlers that see it flip or blit: `Flip_Info` with flip interval 0, `MMIOFlip_Info` with an immediate flip, `MMIOFlipMultiPlaneOverlay_Info` when the flip does not wait for vsync, and `Blit_Info`. `PresentHistory` sets it false. The DXGI `Present_Start` path (`RuntimePresentStart`) stores only `PresentFlags` and `SyncInterval`. A present dropped before any of these events keeps the constructor's `false`, whatever its flags. A dropped present can still show 1: `BlitCancel_Info` discards a blit after `Blit_Info` set the value and does not clear it. | `PresentData/PresentMonTraceConsumer.cpp` (`HandleDXGKEvent`, `HandleDxgkMMIOFlip`, `HandleDxgkBlt`, `HandleDxgkPresentHistory`, `RuntimePresentStart`) | `environment.tearing` uses only displayed rows (`Dropped` 0). Godot W3 run 1 of 4 October had one dropped present, at 6.8 s into the trace (preroll, before the gate interval), with `PresentFlags` 512 (`DXGI_PRESENT_ALLOW_TEARING`) and `AllowsTearing` 0. The earlier rule therefore recorded `tearing: false` for that run. | `l2.presentmon.allows_tearing` counts in `run.json` |
