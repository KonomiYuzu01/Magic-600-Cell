Run in the local Windows session:
`python tools/agents/codex_review.py --kind implement --model gpt-6.1-sol --effort max --packet docs/progress/1.0/packets/renderer/E-2.4-01-sb-probe.md`
Then Claude reviews `changes.patch`, applies it, builds the probe and runs the measurements on the owner's machine (section 7), and removes the worktree with `--cleanup <call-id>`. The Codex sandbox cannot run the GPU work; its acceptance check covers only what the sandbox can prove.

Source: [renderer-experiment-plan](../../renderer-experiment-plan.md) section 5, made standalone. The plan wins where they differ.

## 1. Goal and acceptance
- Goal: find out whether a bare Direct3D 12 renderer draws the full 600-cell at full detail with the most complex turn animation within the selection gate, and establish the drawing method and the resource-sharing path the framework candidates (E-2.4-02, E-2.4-03) reuse.
- Acceptance, in priority order:
  1. The geometry check against `reference_geometry.py` passes (projected vertex positions and per-cell draw counts for three fixed cameras and the start, midpoint and end poses of the W3 turn).
  2. W1–W4 run on the owner's RTX 4070 Laptop GPU.
  3. Three cold W3 runs are judged by `tools/perf/renderer_gate.py`, and the exact label check passes on every run (plan section 2).
  4. A minimal D3D12 resource handoff with fence synchronisation works, both on the same device and to a second device. This is the S-B half of interop only; each framework runs its own smoke test with its actual API.
  5. A cost table (H-06) gives the frame time added by each candidate visual feature, switched on alone at full detail in W3: sticker gaps, outlines, per-sticker transparency with sorting, fog, depth of field, ambient occlusion and MSAA 4x. A feature not measured by the time box is listed as unmeasured, never estimated.
- Non-goals: UI, input beyond camera rotation, Look Lab presets, NVIDIA features, shipping code quality.

## 2. Actual problem and reproduction
- 0.4 draws with Managed DirectX 9 on .NET Framework (`native/NativeFullRenderer.cs`). 1.0 needs a Direct3D 12 base (owner decision, 29 September 2026), and no D3D12 drawing of this model exists yet.
- Expected: a number for each scene, plus a working drawing method.

## 3. Environment and versions
- Base: `main` with `tools/perf/renderer_gate.py`, `tools/perf/check_renderer_assets.py` and this packet merged.
- Windows 11, RTX 4070 Laptop GPU 8 GB, recorded driver; the E-2.4-00 tools at their recorded versions (PresentMon 2.6.0.0, RenderDoc 1.46.0, PIX 2603.25, CMake 4.4.3, Ninja 1.13.2, the Windows SDK and compiler the owner recorded).
- Language: C++20 with the Windows SDK, or C# with a D3D12 binding; the implementer picks one and states why. Shaders in portable HLSL (owner decision, 2 October 2026), compiled with DXC.
- Evidence kind: actual Windows/DirectX and performance, valid only for the built probe identity. Sandbox results are source/fixture only.

## 4. Necessary source and evidence
- Workload assets (synthetic, from the model): `assets/mesh_vertices.f32` (30,480 base vertices, 4 x f32, one cell), `assets/mesh_sticker.u32` (sticker index per base vertex, 433 stickers per cell), `assets/mesh.json` (`offsets`: vertex range per base sticker), `assets/cell_frames.f32` (600 frames, 16 x f32), `assets/slot_piece.u32` (slot to piece, for colour by label). Full detail is 600 x 433 = 259,800 stickers and about 18.3 million projected vertices per frame. The probe may restructure the work (instancing per cell frame, GPU projection, compute) but must draw every sticker of every cell.
- `core.py:34` (`Model`) for loading and the asset hashes; `tools/perf/check_renderer_assets.py` for the digests and counts.
- Geometry reference: the 0.4 projection and sticker shrink live in the retained runtime assembly that `native/NativeFullRenderer.cs` adapts by reflection; they are not in repository source. The probe therefore writes its projection, cell and sticker shrink and turn interpolation as a small Python reference (`reference_geometry.py`) and emits immutable reference outputs. The reference uses the 0.4 camera parameters (`radius`, `angle`, `face_shrink`, `sticker_shrink`) as captured by `CaptureCamera` (`native/NativeHost.cs:492`). A side-by-side image against the 0.4 host at one fixed camera is recorded for the owner; it is not a gate.
- Scenes W1–W4 and the W3 trace contract: plan section 1. Measurement, conditions and the exact label check: plan section 2. Run directory format: `tools/perf/renderer_gate.py` (`run.json` format `magic600-renderer-run-v1`, `presentmon.csv`, `trace.jsonl`).
- Gate: `docs/wiki/decisions/renderer-candidates.md`.

## 6. Constraints and owned files
- Never change `assets/`, model identity, labels or mechanical state. Read assets through their manifest digests.
- No personal session; synthetic labels only (solved, and the scripted W3 turn).
- Owned files: `work/experiments/renderer-sb/**` only. No Managed DirectX DLLs; nothing under `native/` changes.
- NVIDIA-specific features stay off and out of the build.
- Time box: 1.5 days. Stopping optimisation is separate from completing acceptance.
  - **Early pass:** when a drawing method passes W3, stop trying other methods. Still complete items 1–4, then measure as many H-06 features as the time box allows.
  - **Early failure:** when two drawing methods both stay below 50 % of the gate, stop optimising. Still complete items 1, 2 and 4, record the W3 figures, and escalate the drawing method.
  - **Timeout:** deliver what exists. Unfinished items are listed as not done, unmeasured features as unmeasured.
  - The S-A2 and S-D interop smoke tests may start once item 4 exists, whatever S-B's result. Their geometry ports start only after an S-B W3 run on the owner's machine meets the gate.
  - The H-06 table is due on stage day 5 with whatever has been measured.
- `work/experiments/renderer-sb/check_assets.py` first runs `tools/perf/check_renderer_assets.py` (as a subprocess) and then compares the reference outputs written by `reference_geometry.py` with the committed ones, byte for byte. It needs no GPU and no Windows.

## 7. Required return format
- The probe source, a `README.md` with build and run commands, `check_assets.py`, `reference_geometry.py` with its reference outputs, and the trace-log format.
- After the owner's runs, a result card (protocol section 2) with:
  - per-scene fps and p99 from `renderer_gate.py`, the VRAM peak and the label-check result;
  - the drawing method and the handoff result;
  - the H-06 table;
  - which acceptance items are done, not done or unmeasured, and what failed.
