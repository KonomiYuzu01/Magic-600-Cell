# The twist key's stall on the frame thread, 26 November 2026

[The presented-gap page](presented-gap-2026-11-26.md) traced the stutter in LX-2's runtime-losing faults to each turn
key, which held the shell's frame thread inside `m6h_key_down` for about 50 ms (U7 on 25 November: p50 50.9 ms, p99
60.9 ms). This page splits that time and records the change that moves the view's share off the frame thread. The
records and the method are in `work/experiments/key-stall-20261126/`. Every number is a headless run on the owner's
machine of the host library's C interface over the fake core, release build, with the session's journal on the
machine's disk.

## Where the time went

Temporary timers around each part, 55 keys after 5 warm-up keys, p50 in ms (`ks1126-parts-off`, `ks1126-parts-on`):

| Part | Jumble off | Jumble on |
| --- | --- | --- |
| The whole key call | 35.3 | 22.7 |
| The commit: router, command layer, session store | 11.0 | 8.5 |
| ... the twist menu's resolve | 4.8 | |
| ... the kernel's derive | 3.7 | |
| ... the journal frame's write and its `sync_all` | 2.2 (the sync 1.8) | 2.1 (the sync 1.8) |
| The head's adoption build | 9.5 | 2.3 |
| The display host's adoption: its bundle check, then the backend's adoption with a second check | 8.8 | 8.7 |
| The publish: its publication check, then the preparation | 5.7 | 2.7 |

A twist writes no state object, only the journal frame. The sync is a small share: most of the view's work is
SHA-256 over the 259,800-slot arrays, while building them and checking them twice. The fake core has no GPU, so the
real core's adoption and preparation cost more; that is the likely rest of the 50 ms on screen.

## The change

The commit stays where it was and is durable when the key call returns: the command layer and the session store are
unchanged, with their rechecks, their protected-orbit checks, the journal's order and its frozen format. The key call
now hands the new head to a worker thread at the next engine revision and returns that revision. The worker builds
the engine bundle and the view's publication and checks both; the display host takes the checked bundle and the checked
publication without checking them again (`CheckedBundle`, `CheckedPublication`), and the publication's check counts
only while the host's context equals the one it was checked against. The first frame call after the build adopts the
bundle into the core and publishes the view, on the frame thread, as the core requires. A pump, a view job and a
draft wait for a pending build; a frame never does. Keys faster than the builds hand out a revision each, and only the
newest head is built and adopted.

## Before and after in a modelled frame loop

A frame loop on a modelled 60 Hz display with a frame latency of 1, a twist key every 15 frames, 60 keys
(`ks1126-bench-before` on main at `06e3c26d`, `ks1126-bench-after` on the change):

| | Jumble off, before | after | Jumble on, before | after |
| --- | --- | --- | --- | --- |
| Key call, p50 / p99 ms | 39.0 / 48.8 | 11.4 / 18.9 | 24.8 / 32.6 | 8.9 / 15.7 |
| Refreshes that showed no new frame | 121 | 7 | 61 | 1 |
| Key-down to the refresh that shows the press, p50 / p90 ms | 66.4 / 66.6 | 66.4 / 66.6 | 49.8 / 49.9 | 49.8 / 66.2 |

The press reaches the screen at the same median refresh. With Jumble on, the 90th percentile is one refresh later:
some presses are shown a frame later than before. The few missed refreshes left come from key calls longer than one
refresh, which is the commit itself.

## On the real core

The product shell on screen on the owner's machine, one product build made before the change, run with its own host
library and with the change's, interleaved, Jumble off, a turn key every 0.5 s (`ab_keys.py`, `ab_keys_report.py`
and the method in the records' README). Four 90 s runs, 180 keys each, every key with the shell in the foreground
(`ks1126-real-old-new`):

| | before (2 runs) | after (2 runs) |
| --- | --- | --- |
| The key call, p50 ms | 57.2, 57.5 | 17.6, 18.5 |
| Long frame intervals per key, and their length | 1, about 75 ms | 2, about 35 ms |
| Frame interval p99 ms | 74.9, 75.3 | 34.9, 36.1 |
| Refreshes without a submitted frame, per key | 3.33, 3.37 | 1.93, 2.01 |
| Key-down to the confirmed present of the frame showing it, p50 ms | 82.3, 82.4 | 99.1, 99.1 |
| Frames from the key-down to that frame, p50 | 1 | 3 |

The stall was shorter, but the press came one refresh later: the next frame call returned at once (the key call had
already passed a refresh) before the worker's build ended, and the build was adopted only after the frame after that.
The frame call now waits up to 12 ms after its submission for a pending build. In four interleaved 60 s runs
(`ks1126-real-wait`) the frame that shows the press moved from the third after the key to the second, and the one run
with confirmed presents with the wait showed it at 82.3 ms (25 keys), as before the change. The owner returned to the
machine during these runs, so three of the four had no foreground and few confirmed presents.

Temporary timers in the change's host on screen (`ks1126-real-publish`, p50): the worker's build 10.7 ms; on the frame
thread, the core's adoption 0.2 ms and the publish 15.3 ms, of which the core's `sa2_prepare` 11.3 ms, the admission's
`describe_backend` 1.4 ms and the pump after it about 2 ms. `sa2_prepare` creates a command allocator, a command list
and three buffers (two 1 MB, one 2 MB upload) for every preparation, so every twist creates GPU resources on the frame
thread. The commit (18 ms here) and that preparation are what is left, each over a refresh.

## The rest removed: the core's preparation and the menu's resolve

The owner chose to remove what was left before U7 (26 November 2026). Both parts were timed headless on the owner's
machine; the records' README has the method.

- **The core's `sa2_prepare`** took p50 10.1 ms, p99 15.0 ms on the hardware adapter over 200 preparations, each
  activated and its predecessor retired as the shell does per twist (`ks1126-prepare-before`). Timers split it: 9.0
  ms was the conversion of the caller's arrays, whose check of each of the 259,800 slots built a `std::string` of its
  message every time; creating the GPU resources was under 1 ms. The check now builds its message only for a failure,
  and a preparation reuses the allocator, list and upload buffer of a completed upload and the buffers of a released
  set instead of creating them (at most two of each kept, none after a device removal). After: p50 1.2 ms, p99 1.7 ms
  (`ks1126-prepare-after`).
- **The menu's resolve** built the 60-item menu's exact twists at the twist's cap on every commit. A menu now keeps
  the twists of the 32 caps used most recently and reuses them only while the model identity, frame and pole they were
  built from are the context's, so every answer is a fresh build's; the commit is otherwise unchanged. In interleaved
  runs over the fake core, with the owner using the machine, the key call fell from p50 12.8 to 7.3 and 7.7 ms with
  Jumble off (`ks1126-memo-without`, `ks1126-memo-with`) and from 10.2 and 10.0 to 4.9 and 5.2 ms with Jumble on: about 5 ms per key.

## What it does not show

The part tables and the modelled frame loop are headless runs over the fake core. The on-screen runs show what the
shell's own logs record on one machine, with a key posted every 0.5 s from a script; they are not LX-2's conditions,
and none is a phase pass (PHS.64, PHS.66). LX-2's device run (U7) on the owner's machine is the measurement. The
commit is untouched: its largest part, the menu's resolve, is a pure function inside the command layer.
